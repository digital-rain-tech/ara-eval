## Findings

### Medium

#### 1. Retry runs can blend prior results with the current model identity

- File: `labs/lab-01-risk-fingerprinting.py`
- Line: 274
- Severity: medium
- Category: Diff
- Description: `--retry` retains successful evaluations from the prior JSON but writes `_run.model_requested` from the current `MODEL`. If a user retries without exporting the same `ARA_MODEL`, the output can contain fingerprints from multiple models while claiming the whole run used the current model. That can corrupt leaderboard inputs and make model comparisons misleading.
- Suggested fix: Store the prior run model separately and require it to match the current `MODEL` unless an explicit override is provided. Preserve per-evaluation `model_used` for retained entries and surface a mixed-model warning when any retained result differs from the retry model.

#### 2. Retry run database summaries do not match the request rows they summarize

- File: `labs/lab-01-risk-fingerprinting.py`
- Line: 185
- Severity: medium
- Category: Diff
- Description: Retry mode seeds `run_stats` with prior successful evaluations, but the new SQLite `eval_runs` row only has provider request rows for calls made during the retry under the new `run_id`. The resulting run summary can report successful calls, tokens, cost, and duration that have no matching `ai_provider_requests` rows for that `run_id`, which breaks traceability for reports, audits, and request-log inspection.
- Suggested fix: Keep DB run statistics scoped to calls made in the current invocation, or explicitly copy/link prior request rows into the retry run with provenance metadata. If the JSON output remains cumulative, maintain separate cumulative output metadata and per-run DB metadata. Add a regression test with one prior success and one retried failure.

#### 3. Retry overwrites the prior result file non-atomically

- File: `labs/lab-01-risk-fingerprinting.py`
- Line: 302
- Severity: medium
- Category: Diff
- Description: When `--retry` is used, `output_path` is the prior results file and the code writes JSON directly to that same path. If the process is interrupted or crashes during `json.dump`, the original partial run can be truncated or corrupted, losing the data retry mode depends on.
- Suggested fix: Write to a temporary file in the same directory and atomically replace the original with `Path.replace()` after a successful write. Consider keeping a `.bak` copy of the prior results file before replacement.

#### 4. Core Python module has too many responsibilities for reliable agent edits

- File: `ara_eval/core.py`
- Line: 1
- Severity: medium
- Category: Holistic
- Description: `ara_eval/core.py` is the documented single source of truth, but it combines environment loading, configuration, prompt rendering, SQLite schema and migrations, request logging, OpenRouter calls, JSON repair and parsing, gating, scenario loading, retry helpers, and CLI printing in one large file. That makes ownership boundaries hard to see and increases the chance that an agent changing prompt logic, persistence, or provider behavior affects unrelated code.
- Suggested fix: Split by stable responsibility, such as `config.py`, `prompts.py`, `db.py`, `providers/openrouter.py`, `parsing.py`, `gating.py`, and `cli_output.py`. Keep a compatibility layer in `core.py` while labs migrate gradually.

#### 5. Web and Python implementations duplicate evaluation semantics

- File: `web/src/lib/openrouter.ts`
- Line: 2
- Severity: medium
- Category: Holistic
- Description: The web code mirrors Python behavior across prompt rendering, OpenRouter calls, validation, SQLite schema, and gating. This creates two sources of truth for evaluation semantics. Drift is structurally likely because provider defaults, schema logic, and parsing behavior must be kept aligned manually across Python and TypeScript.
- Suggested fix: Move shared constants and golden behavior fixtures into a versioned contract. Add parity tests that compare Python and TypeScript outputs for prompt assembly, gating, JSON parsing, and request defaults. Where possible, generate TypeScript constants or types from `shared/*.json`.

#### 6. Public history APIs expose raw prompts and responses without access control

- File: `web/src/app/api/requests/route.ts`
- Line: 4
- Severity: medium
- Category: Holistic
- Description: `/api/requests` returns rows from `ai_provider_requests`, including raw request and response data returned by the database layer. In a deployed web app, this can disclose scenario text, full prompts, model responses, internal metadata, errors, and potentially sensitive user-entered evaluation content. There is no authentication, environment guard, or route-level redaction.
- Suggested fix: Restrict diagnostic/history routes to local development or authenticated admin users. Return redacted summaries by default and require an explicit privileged path for raw request/response inspection. Add tests asserting raw payload fields are not exposed in production responses.

#### 7. Required web environment validation logs but does not fail fast

- File: `web/src/lib/env.ts`
- Line: 17
- Severity: medium
- Category: Holistic
- Description: The comment says required env vars should fail fast, but the implementation only logs when `OPENROUTER_API_KEY` is missing and lets the server continue. Deployment health becomes ambiguous, and failures surface later inside individual API requests.
- Suggested fix: Replace the log-only behavior with a startup validation helper that throws in production/server contexts when required variables are missing. Document optional variables such as `ARA_MODEL`, and add a validation test for missing required environment behavior.

#### 8. Agent guidance is only at the repository root and is too thin for major subtrees

- Directory: `labs/`, `web/`, `prompts/`, `scenarios/`, `shared/`, `tests/`
- Severity: medium
- Category: Holistic
- Description: The only `AGENTS.md` is at the repo root and simply points to `CLAUDE.md`. Major areas have different operating rules: labs write result artifacts and DB rows, prompt files are part of the evaluation contract, shared JSON feeds the public site, and web routes can expose server-only data. Without local guidance, agents can miss subtree-specific invariants and validation commands.
- Suggested fix: Add focused `AGENTS.md` files for `labs/`, `web/`, `prompts/`, `scenarios/`, `shared/`, and `tests/`. Include file purposes, generated-output handling, validation commands, common pitfalls, and compatibility checks. If Claude Code compatibility is required, add matching `CLAUDE.md` symlinks or document why root-level guidance is sufficient.

### Low

#### 9. Retry success detection accepts incomplete prior evaluations

- File: `labs/lab-01-risk-fingerprinting.py`
- Line: 185
- Severity: low
- Category: Diff
- Description: Retry success detection treats any evaluation with `fingerprint` and no `error` as reusable, then later assumes `ev["gating"]` exists. A malformed or older results file with a fingerprint but missing gating will raise `KeyError` and abort retry before reaching remaining failed calls.
- Suggested fix: Validate the full expected shape before adding an evaluation to `skip_set`, including `fingerprint`, `gating`, and any fields needed for delta/stat reconstruction. Treat incomplete entries as retry candidates.

#### 10. Latest-result symlink assumes retry files live under `results/`

- File: `labs/lab-01-risk-fingerprinting.py`
- Line: 308
- Severity: low
- Category: Diff
- Description: `latest_path.symlink_to(output_path.relative_to(results_dir.resolve()))` assumes the output path is under `results/`. The `--retry` argument accepts any existing path, so retrying a file outside `results/` can complete the write and then crash with `ValueError` while creating the symlink.
- Suggested fix: Require retry files to live under `results/` and validate that before running, or use an absolute symlink target or fallback when `output_path` is outside `results_dir`.

#### 11. README leaderboard regeneration command is stale

- File: `README.md`
- Line: 58
- Severity: low
- Category: Holistic
- Description: The README says to run `python labs/update-readme-leaderboard.py`, but the documented workflow and current script are `python labs/publish-leaderboard.py`. This can send contributors or agents looking for a non-existent or obsolete script.
- Suggested fix: Replace the line with `python labs/lab-04-inter-model-comparison.py`, then `python labs/publish-leaderboard.py`. Consider adding a CI check that README command snippets reference existing files.

#### 12. Python type checking is not part of the project contract

- File: `pyproject.toml`
- Line: 1
- Severity: low
- Category: Holistic
- Description: The Python package uses some type hints, but there is no mypy or pyright configuration and CI only runs tests. Result dictionaries and provider responses pass through many layers, so type regressions can slip through unless a runtime test happens to cover them.
- Suggested fix: Add gradual type checking for the core package first, such as pyright or mypy in non-strict mode. Start with `ara_eval/` and key lab helpers, then tighten around result schema objects.
